## New P2: `iam` mode likely breaks `/deliveries`

- **What the app does:** `/deliveries` re-validates the Cloud Tasks Google token's signature in the container (`runtimequeue/runtime.go:176-204`). Cloud Tasks sends that token in `Authorization`.
- **What I expect from Cloud Run:** with Invoker IAM on, Cloud Run checks that same header and, from memory, forwards it with the signature replaced. This is unverified.
- **Scenario:** a framework config with `gcp.invocation: "iam"` validates and generates a plan. Every queued command and replay then gets 401 at `/deliveries`, and Tasks retries indefinitely.
- **Gap in the current guard:** the `iam` REVIEW note (`plan.go:73`) covers application-bearer clients only, not delivery.
- **Fix:** check the official docs, then either reject `iam` for framework runtime with GCP delivery in `Validate`, or extend the REVIEW note. The checked examples are unaffected.

## P3

- **Log wiring is ungated:** no test fails if `serviceapp/app.go:99` or `cmd/framework/main.go:53` drops the callback. The integration app at `framework_flow_test.go:356` passes no `OnRejected`, and the HTTP path has no failing-observer case. One counter assertion in that flow would cover both.
- **Runtime log is not JSON:** `cmd/framework/main.go:52` uses `slog.Default()`, which is the text handler. The test builds its own JSON handler, and `cmd/dia/main.go:33` sets JSON. The README's "structured warning" is only true after a one-line handler change.
- **Zero clock leeway:** the token has `nbf = now` (`internal_token.go:68`) and verification allows no skew (`dia/auth.go:52`). An operator workstation one second ahead gets a 401 that looks like a wrong credential. The integration fixture backdates by one second (`framework_flow_test.go:87`).
- **"wrong-audience" label:** that subtest changes the network, so the issuer changes too and rejection happens before the audience check. Audience-only mismatch is covered at the owner (`dia/auth_test.go:103`), and `capabilities.md:725` words it accurately.
- **Local mode:** `blossm replay` requires HTTPS (`workflows.go:144`) and `internal-token` requires a valid deployment config. A loopback local process therefore needs a plain HTTP client with the minted token.
- **DLQ prerequisite placement:** it appears in the architecture and package READMEs but not in the `Prepare` prerequisites operators review.

## JS comparison

- **Internal auth:** `vendors/gcp/token/test/index.js:33-43` asserts a metadata identity token with the Cloud Run URL as audience, so JS internal calls relied on platform IAM. Go's application JWT with an explicit mode is a deliberate replacement, which is why the `iam` case above matters.
- **Queue dispatch:** `vendors/gcp/queue/test/index.js:79-98` asserts OIDC with the URL origin as audience. Go uses an explicit configured audience and verifies in the container.
