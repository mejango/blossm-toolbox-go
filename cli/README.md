# Blossm offline CLI

The CLI uses strict versioned JSON, a deliberate internal redesign of Toolbox's
YAML/template system. One module owns the complete runtime. It does not recreate
154 npm modules or silently provide successful deployment stubs.

From the Go module root, first fetch reviewed dependencies and compile the CLI:

```sh
go mod download
go build -mod=readonly -trimpath -o bin/blossm ./cmd/blossm
bin/blossm init --provider gcp --database postgres --config blossm.json
bin/blossm validate --config blossm.json
bin/blossm plan --config blossm.json
bin/blossm deploy --dry-run --config blossm.json
bin/blossm generate --config blossm.json --out deploy/generated
bin/blossm test
bin/blossm test --race
POSTGRES_URL='...' MONGODB_URI='...' bin/blossm test --integration --race
bin/blossm build --out bin
```

`init` refuses to overwrite a file. It creates example identifiers with mode0600;
replace them with your reviewed resources and image. `validate` rejects unknown
fields, duplicate JSON keys, multiple JSON values, invalid provider/database
selection, cloud local-mode bypass, malformed resource/secret references and
reserved secret environment names. Configuration is limited to1MiB.

`plan` and `deploy --dry-run` print the same deterministic JSON and write nothing.
`generate` writes provider artifacts plus `plan.json` to a new directory, refusing
to replace existing output. All preparation commands are offline and do not
invoke gcloud, AWS CLI, Docker, a provider SDK or a database. Printed review
commands are data by default. `deploy` without flags also prepares offline; only an
explicit `--execute` invokes the provider. `--execute --dry-run` is rejected.

`test` invokes actual Go tests in `--dir` (default current directory), propagating
subprocess failure/exit status. `--race` enables the race detector; `--integration`
requires both POSTGRES_URL and MONGODB_URI and enables the integration build tag.
`build` compiles cmd/blossm, cmd/dia and cmd/framework. A missing executable
or compilation errors fail the build. Neither command claims success on missing
source or prerequisites. Both set GOPROXY=off, GOSUMDB=off, GOTOOLCHAIN=local and
GOWORK=off, so dependencies/toolchain must already be available. Tests themselves
may open local/native resources according to their suite contracts; the command
does not sandbox arbitrary test code.

The two checked [deployment examples](../deploy/examples) are generated by
`init` and verified byte-for-byte by `TestCheckedExamples`; they cover primary GCP
with PostgreSQL and AWS with Mongo. Tests exercise all four provider/database
combinations. Provider schemas, runtime environment names, IAM/networking
prerequisites and build pins are documented in [deployment preparation](../deploy/README.md).

## Retained procedure and operational workflows

Generate typed adapters in the existing module, with no nested go.mod:

```sh
bin/blossm scaffold --dir . --kind command --name register_project
bin/blossm scaffold --dir . --kind fact --name project_state
```

Kinds are command, fact, job, projection, event-store, view-store, view-composite
and gateway. They inject required business behavior rather than returning fake
success. Job/reducer/projection/gateway adapters fail when required handlers are
absent. Commands/facts reuse their existing framework owners. Projection templates
bind authoritative root/version before persistence. Gateways require an explicit
authentication/permission callback. Register generated handlers in cmd/dia.
Scaffolding refuses an existing output directory; source is gofmt-formatted.

The following commands prepare offline by default. Add `--execute` only when
intentionally invoking a configured provider/endpoint in a future authorized run.
These examples were verified through isolated fake runners, not live providers.

```sh
# Authenticated operation invocation; provide the exact application's endpoint.
bin/blossm job --config blossm.json --url https://service.example/jobs/example --input job.json --bearer-env BLOSSM_BEARER_TOKEN --idempotency-key stable-job-identity
bin/blossm replay --config blossm.json --url https://service.example/projections/example/replay --input replay.json --bearer-env BLOSSM_BEARER_TOKEN --idempotency-key stable-replay-identity
# Upload reviewed application role definitions, without changing IAM.
bin/blossm roles --action upload --config blossm.json --input roles.json --destination gs://example-bucket/roles.json
# Supply secret bytes in SECRET_VALUE, never as a command argument.
bin/blossm secret --action create --config blossm.json --name dia-hmac-key --value-env SECRET_VALUE
bin/blossm secret --action put --config blossm.json --name dia-hmac-key --value-env SECRET_VALUE
bin/blossm queue --action create --config blossm.json --name projection-queue --rate 100 --concurrency 10
bin/blossm queue --action update --config blossm.json --name projection-queue --rate 50 --concurrency 5
bin/blossm queue --action delete --config blossm.json --name projection-queue
bin/blossm deploy --config blossm.json
# AWS existing service: same config owner, exact registered revision is injected.
bin/blossm deploy --config deploy/examples/aws-mongo.json --update
```

AWS roles use s3:// destinations. AWS secrets use names/ARNs and create-secret or
put-secret-value; secret stdin uses the AWS CLI file loader's `/dev/stdin`, so
execution requires a Unix-like environment. GCP secret creation uses automatic
replication and adds a version; put only adds a version to an existing secret.
No command adds IAM grants. AWS queue create takes a name; update/delete take a
regional HTTPS queue URL; `--visibility` configures its0–43200second timeout.
GCP queue create/update take explicit rate/concurrency. Queue deletion is an
explicit action and still requires `--execute` to mutate anything.

Job/replay execution requires a nonempty named bearer environment and a stable
idempotency key. Remote endpoints require HTTPS; HTTP is permitted only for localhost or literal loopback IPs. URLs must not contain credentials/query/fragment. Input is
bounded JSON. Authentication policy belongs to the target handler; the client
does not guess endpoint paths or mint an unbound token. HTTP failures propagate,
there is no automatic write replay, and a lost response may require an identical
idempotent retry. A successful HTTP response is not proof of all follow-up work.

Cloud execution uses `exec.CommandContext` argv, never shell interpolation.
Secret values are resolved only during execution, passed via stdin and excluded
from serialized plans/argv. Runner failures stop later operations and preserve
nonzero exit status; earlier provider effects may already have committed.
Cloud Run replacement waits via gcloud. AWS registers a task definition, validates
its returned ARN, binds that exact revision into create-service/update-service,
and waits for services-stable. Provider readiness does not establish application
health; the output states that limitation. Temporary deployment files are removed.

`RunWith(..., Execution{Runner: fake, HTTP: fixture, Getenv: fixture})` is the test
seam. Every provider workflow is tested with isolated injected runners, including
argv/stdin, deployment revision binding, denied operations, missing secret input,
HTTP authentication/failures and no execution during preparation. Native cloud
execution was not performed. The full selected-toolchain/container/dependency
verification remains the parent integration gate.

## Developer service identity

Preparation is offline and prints argv only. Acquisition requires explicit execution:

```sh
blossm token --config blossm.json --audience https://SERVICE.run.app
blossm token --config blossm.json --audience https://SERVICE.run.app --impersonate-service-account caller@PROJECT.iam.gserviceaccount.com --execute
```

Execution prints the sensitive GCP identity token to stdout. Existing gcloud
credentials and appropriate audience/impersonation authority are required;
this command grants no IAM privileges and does not mint an application JWT.
The [official gcloud command](https://docs.cloud.google.com/sdk/gcloud/reference/auth/print-identity-token)
accepts one audience. Offline tests inject the runner; no live token was acquired.
AWS deliberately has no equivalent bearer-token command: use
`cloud/aws.ServiceAuth.Sign` with explicit credentials, region and service for
SigV4-authenticated AWS requests. Application ES256 JWT/Bearer authentication
is a separate contract from either provider's outbound service authentication.

Job scaffolds construct `job.Procedure`; projection scaffolds construct
`projection.Engine` and `projection.Scheduler`; composite scaffolds delegate to
`view.ExecuteComposite`. Their owners enforce validation, scope and execution
rules. Generated-module tests compile all kinds and exercise missing-dependency
rejection through the owning APIs.

AWS publication config requires exact queueARN, rawMessageDelivery=true and
maximumMessageSize>=262144. Plans include separate publication preparation argv
and artifacts; see the deployment guide for application and verification steps.

Gateway scaffolds expose `New(ctx, serviceapp.Config)` and delegate to
`serviceapp.New`, which composes the document command, fact, job, projection,
named view, internal store/delivery routes and Dia identity HTTP routes. Supply
separate identity/document backend namespaces and outboxes, the exact trusted
internal service verifier, and the selected queue/replay/publication adapters.
The returned `App.Handler` is an actual HTTP handler; the caller owns the HTTP
server, background workers, cancellation and backend closure. The parent-owned
`cmd/framework` provides process/environment composition. The scaffold neither
creates databases nor executes cloud resource commands.

Custom gateway extensions use the [owning transport contract](../transport/tasks/auth_gateway.md):
register exact `GatewayRoute` policies with required resource `Check`, using
`DiaVerifier` or a subject-pinned `ServiceJWTVerifier`. Browser credentials are
opt-in typed `{type,value,expires}` cookie contributions with `__Host-` names,
exact HTTPS origins and CSRF checks. Uploads require explicit limits and storage;
`FactProxy` requires a fixed RPC destination and an `Upstream` credential callback.
The generator delegates default route composition to `serviceapp`; it does not
install permissive extension policies.

Deployment configs require `runtime: "dia"` or `"framework"` and explicit
`signing.provider: "local"|"gcp"|"aws"`. Cloud signing requires `signing.kmsKey`
and a `JWT_PUBLIC_KEY` secret reference; local signing requires `JWT_PRIVATE_KEY`.
Mixed private/KMS settings fail validation. Framework configs additionally require
`service`, `internalSubject`, distinct `identityNamespace`, and `delivery` resources.
See the [framework examples](../deploy/examples/gcp-framework-postgres.json) and
[deployment contract](../deploy/README.md). Plans select `/framework` explicitly;
queue and publication preparation remains offline and never discovers credentials.

For nested commands, `DelegatedCommandAuthorizer` requires authenticated parent
Main context, a signing JWT whose audience is the exact target `network/service`,
a fixed outbound RPC endpoint and `CommandClient.Target`, exact peer subject,
and the shared Dia state service. The child uses `DelegatedCommandGateway` or
`DelegatedCommandVerifier` with mandatory `DelegatedCommandCheck`, alongside
explicit command/resource permissions. These command credentials are separate
from delivery, store-peer and job credentials; do not reuse their verifiers.

Replay input is the owning `ProjectionReplayInput`, for example
`{"runId":"rebuild-2026-11-12-01","after":"","limit":100}`. `runId` is required
and must stay unchanged across retry and pagination; start a deliberate new run
with a new ID. `after` is the confirmed cursor returned by the previous page.
Replay URLs must explicitly select `/projections/{name}/replay`. The CLI uses
`ProjectionClient` to reject malformed or foreign-run acknowledgments, including
HTTP200 with `null` or `{}`. No static delivery run ID or environment fallback
exists; the HTTP idempotency header does not replace the logical replay run ID.

## Internal service token issuance

`internal-token` issues the application service credential for configured internal
routes, including replay and rejection inspection. It is distinct from `token`
(Google invocation identity) and from delegated-user command credentials.

```sh
# Preparation does not read credentials or open a signer.
bin/blossm internal-token --config blossm.json --ttl 2m
# Explicit future invocation: stdout contains only the sensitive JWT.
bin/blossm internal-token --config blossm.json --ttl 2m --execute
```

The framework config fixes `internalSubject` and network audience; there are no
subject/audience override flags. TTL defaults to5m and is limited to1s..5m.
Before explicit execution, load the matching `JWT_SIGNER` and signing-key
variables from the already-authorized secret source: local PKCS8 P256 private
PEM, or cloud KMS key and pinned public PEM. They must correspond to the config's
secret references. `runtimeauth.Open` and `dia.JWT.Sign` perform the signing;
the CLI does not fetch secrets or grant signer access. Cloud execution can call
KMS and requires its existing authority. Do not log or commit stdout tokens.
Supply the resulting token through the replay command's named bearer environment.
Tests use synthetic local keys and injected KMS clients only.

GCP config additionally requires explicit `gcp.invocation: "application"|"iam"`.
The generated plan flags the selected provider check for review; see
[invocation requirements](../deploy/README.md#cloud-run-invocation-and-application-credentials).

Internal service JWTs use strict timestamp validation. The signing workstation and
service clocks must be synchronized; the issuer does not silently extend the
validity window with clock-skew allowances.

Framework GCP plans require `gcp.invocation: "application"`. The IAM mode is
rejected for this composition because intact Cloud Tasks token forwarding to the
in-container signature validator has not been verified. Dia IAM mode still
requires the explicitly configured authenticating edge described in deployment
docs. Local `job`/`replay` requests can use `http://localhost`, `127.0.0.0/8` or
IPv6 loopback literal addresses; remote plaintext HTTP remains rejected before
credential access. DNS names resolving to loopback do not qualify automatically.
